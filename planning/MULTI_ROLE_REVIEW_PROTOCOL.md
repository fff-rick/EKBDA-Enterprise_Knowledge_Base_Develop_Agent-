# 多角色只读评审协议

## 目标

多角色评审用于在代码修改前，从产品、技术和运维视角检查已生成的实施计划，输出可追溯的共识、风险和待人工决策事项。所有角色只能读取同一份授权上下文，不得修改仓库、执行命令或替代人工批准。

## 角色与责任

| 角色标识 | 职责 | 不负责 |
|---|---|---|
| `product_research_analyst` | 用户价值、市场与竞品假设、证据缺口 | 编造外部调研事实或决定商业方向 |
| `product_manager` | 目标、范围、非目标、验收标准和业务流程 | 批准技术风险或生产发布 |
| `backend_engineer` | 服务边界、接口、数据、兼容性、性能和后端测试 | 决定产品优先级 |
| `frontend_engineer` | 交互、客户端契约、兼容性、可访问性和前端测试 | 默认扩大前端改造范围 |
| `operations_engineer` | 部署、配置、容量、可观测性、告警和回滚 | 登录生产环境或绕过发布审批 |
| 协调器 | 汇总共识、冲突来源和决策选项 | 添加新事实或作出最终决定 |

## 工作流

1. 实施计划生成后进入 `awaiting_role_review`。
2. 五个角色基于同一次重新授权采集的知识、规范和 Git 元数据并行独立评审。
3. 每份评审必须包含结论、建议、结构化发现、开放问题和引用 ID。
4. 协调器只读取五份评审，形成共识和 `decision_items`。
5. 没有待决策项时进入 `awaiting_approval`；存在待决策项时进入 `awaiting_resolution`。
6. `project_approver` 或 `knowledge_admin` 逐项记录决议；会话创建者不能自行解决冲突。
7. 全部决议完成后进入 `awaiting_approval`，再执行原有四眼批准或拒绝。

## 输出约束

- `recommendation` 只能为 `approve`、`approve_with_conditions` 或 `reject`。
- 发现严重性只能为 `info`、`warning` 或 `blocking`。
- 知识和规范引用必须来自当前评审上下文的 `K*`、`S*` 白名单。
- 协调器的待决策项必须标记来源角色，并提供两个至五个可讨论选项。
- Provider 不能预填人工决议、决议人或决议时间。
- 会话仅持久化知识文档 ID、版本、切片号和摘要哈希，不保存检索片段正文。

## 审计要求

每次角色评审、冲突决议和最终批准都会增加会话 `revision` 并写入不可变事件。调用方必须使用当前修订号，过期请求返回冲突。人工决议应说明选择、必要条件和风险接受责任，不应只填写“同意”。
