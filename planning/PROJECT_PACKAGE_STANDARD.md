# 新项目立项包标准

## 1. 适用范围

本标准约束 EKBDA 从已批准规划会话生成、发布、评审和导出的项目立项包。立项包是详细设计与受控开发的标准输入，不替代预算审批、架构委员会审批、安全审批或生产发布审批。

立项包生成只整理已批准事实，不授予代码修改、合并、外部网络访问、基础设施变更或部署权限。

## 2. 发布前提

仅当规划会话同时满足以下条件时允许发布：

- 状态为 `approved`，并保留批准人、批准时间和批准时的修订号。
- 产品调研师兼竞品分析师、产品经理、运维工程师、后端开发、前端开发五个角色均已独立完成评审。
- 协调器产生的所有待决策事项均由授权人员完成决议。
- 规划阶段与角色评审阶段的知识、规范上下文快照哈希完整。
- 调用者具有 `project_approver` 或 `knowledge_admin` 角色，并通过项目/仓库 ACL。

## 3. 固定交付物

每个版本必须且只能包含以下七类交付物；缺少、重复或出现未知类型均拒绝发布。

| 类型 | 最低内容要求 |
|---|---|
| `prd` | 目标与价值、范围与非目标、业务验收标准 |
| `architecture` | 总体设计、组件边界、数据流、关键约束和架构决策 |
| `api` | 契约范围、请求响应、错误语义、鉴权、兼容与幂等要求 |
| `test` | 验收测试、单元/集成/回归策略、质量与安全门禁 |
| `deployment` | 环境前提、部署步骤、人工审批、验证和回滚 |
| `monitoring` | 业务与技术指标、告警、责任人和上线观察窗口 |
| `risk` | 实施风险、多角色共识、人工决策和风险接受记录 |

## 4. 引用边界

交付物引用由 `kind + id` 唯一标识，必须命中来源会话的对应白名单：

- `plan_knowledge`：实施计划上下文中的知识 `K*`。
- `plan_standard`：实施计划上下文中的规范 `S*`。
- `review_knowledge`：多角色评审上下文中的知识 `K*`。
- `review_standard`：多角色评审上下文中的规范 `S*`。
- `decision`：已经人工解决的决策项 `D*`。

不同上下文中的同名 ID 可能指向不同对象，不得省略 `kind`。Provider 不得引用未解决决策，也不得臆造端点、架构事实、指标数值、竞品结论或生产状态。

## 5. 需求追踪矩阵

立项包必须为 PRD 中每个唯一条目生成一条追踪记录，并满足：

- `requirement_id` 按 PRD 出现顺序稳定编号为 `REQ-001`、`REQ-002`……
- `requirement` 必须与 PRD 条目原文完全一致，不允许增加、遗漏或重复。
- 架构、测试和部署引用必须精确命中对应交付物的章节名。
- 适用 API 的需求必须引用 API 章节；不适用时必须给出明确原因且不得填写 API 章节。
- 服务端重新计算 `coverage_status` 和 `gaps`，不信任 Provider 自报的覆盖结论。
- 追踪矩阵属于版本定义，参与 `definition_hash` 计算。

`covered` 表示架构、API（如适用）、测试、部署链路齐全；`partial` 表示仍有缺口。部分覆盖可用于显式暴露待办，但不能被解释为已满足后续质量或发布门禁。

## 6. 版本与不可变性

- 版本身份为 `project + name`，每次发布自动递增版本。
- 历史版本不可覆盖；变更必须以新版本和新的 `change_summary` 发布。
- 每个版本保存来源规划会话、修订号、上下文哈希、批准人和批准时间。
- `definition_hash` 覆盖项目、仓库、包名、变更说明、Provider、来源快照、七类交付物和追踪矩阵。
- Markdown/DOCX 导出是确定性视图，不创建新版本、不修改定义哈希。

## 7. 单交付物评审

评审记录与立项包分离，以追加方式保存，不修改已发布版本：

- 评审对象必须是七类固定交付物之一。
- 请求必须携带当前 `package_hash`；与目标版本不一致时返回冲突，防止误评旧内容。
- 决策仅允许 `approve` 或 `request_changes`。
- 评审意见不能为空，最大 4000 字节，并记录评审人、UTC 时间和交付物内递增序号。
- 只有 `project_approver` 或 `knowledge_admin` 可提交评审；项目授权成员可读取评审。
- `request_changes` 不原地修改交付物。修改应回到规划/设计流程，发布新的立项包版本后重新评审。

## 8. 导出标准

系统支持：

- `markdown`：包含版本元数据、追踪矩阵、全部交付物、引用和评审记录。
- `docx`：Letter 纵向、1 英寸页边距、层级标题、真实项目符号、固定列宽表格、重复表头、页眉和页码；不包含个人作者元数据。

导出接口必须执行与读取立项包相同的项目/仓库 ACL。导出内容不得声明代码、部署或生产验证已经完成。

## 9. 验收标准

一个版本达到本阶段交付标准时，应同时满足：

- 七类交付物和追踪矩阵通过服务端结构与引用校验。
- 版本号、来源快照和定义哈希持久化正确。
- 评审哈希冲突、非法决策、越权操作均被拒绝。
- Memory 与 PostgreSQL 存储语义一致，评审序号并发安全。
- Markdown/DOCX 均可导出；DOCX OOXML 可解析，表格首行标记为表头，无高/中/低级可访问性问题。
- 单元测试、HTTP 生命周期测试、`go vet` 和构建通过；PostgreSQL 集成测试在提供测试 DSN 时通过。
